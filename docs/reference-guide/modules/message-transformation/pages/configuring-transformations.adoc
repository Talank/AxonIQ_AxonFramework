= Configuring Transformations
:navtitle: Configuring transformations

Individual transformations are assembled into an `EventTransformerChain` and registered once with your configuration.
Axon Framework then applies the chain whenever events are read from the store.

== Registering the chain

Build the chain with the transformers in the order they should run:

[source,java]
----
public static EventTransformerChain chain() {
    return EventTransformerChain.builder()                            // <1>
                                .register(SystemAnnouncementLegacyUplift.build())
                                .register(CoursePublishedV1ToV2.build()) // <2>
                                .register(CoursePublishedV2ToV3.build())
                                .register(StudentRegisteredV1ToV2.build())
                                .register(WelcomeMessageBetaCleanup.build())
                                .build();                             // <3>
}
----
<1> Start building the chain.
<2> Each transformer runs in the order it is registered — see <<_why_ordering_matters>>.
<3> `build()` produces an immutable chain, ready to register as a component.

Then make that chain available to your configuration as an `EventTransformerChain` component.
You only ever supply the chain: a transformation enhancer detects that component and installs the event-store transformation for you, so there is nothing to wire on the event store itself.
How you register the component depends on your setup:

[tabs]
====
Declarative - Configuration API::
+
--
Register the chain as a component on your `EventSourcingConfigurer`:

[source,java]
----
configurer.componentRegistry(registry -> registry
        .registerComponent(EventTransformerChain.class,            // <1>
                           config -> CourseCatalogTransformations.chain()));
----
<1> Register the chain under `EventTransformerChain.class`. Axon Framework's transformation enhancer detects this component and decorates the event store with it.
--
Autodetected - Spring Boot::
+
--
Expose the chain as a bean of type `EventTransformerChain`; Axon's Spring Boot integration registers it as a component, where the same enhancer detects it:

[source,java]
----
@Bean
public EventTransformerChain eventTransformerChain() {
    return CourseCatalogTransformations.chain();
}
----
--
====

Both approaches do the same thing — provide one `EventTransformerChain` component — and the event store then applies it on every read.
Register no chain and the event store is left untouched.

The chain is built once at startup and is immutable afterwards.
The `chain()` shown above is the one assembled in the xref:message-transformation:demo.adoc[course catalog example].

[#_why_ordering_matters]
== Why ordering matters

A stored event flows through the chain, with each matching transformer's output feeding the next, until no further transformer matches.
Register transformers in version order so each hop hands off to the one after it:

[source,java]
----
.register(CoursePublishedV1ToV2.build())   // 1.0.0 -> 2.0.0
.register(CoursePublishedV2ToV3.build())   // 2.0.0 -> 3.0.0
----

A stored v1 `CoursePublished` is lifted to v2 by the first transformer, then that result is lifted to v3 by the second, so your handler always receives the current shape.

[TIP]
.Prefer small, single-step transformations
====
Write one transformer per version step — `v1` to `v2`, then `v2` to `v3` — rather than a single transformer that jumps straight from `v1` to `v3`.
This is the incremental approach Greg Young recommends for versioning in event-sourced systems: each step stays small, isolated, and easy to reason about, and adding a new version means appending one more transformer while the chain keeps composing the steps for you.
====

[NOTE]
.Safety bound
====
The chain stops re-applying transformers to an event after a fixed number of hops (100 by default) to guard against accidental cycles.
If a single event legitimately needs more hops, raise the bound with `EventTransformerChain.builder().maxIterationsPerEvent(int)`.
====

[#_when_more_than_one_transformation_matches]
== When more than one transformation matches

Chaining handles the common case where each transformer matches a _different_ identity and hands off to the next.
Registration order also resolves the rarer case where _several_ registered transformations match the _same_ stored event — most often a broad predicate that overlaps a specific `from`.
When that happens the chain applies the *last* matching registration: later registrations override earlier, overlapping ones.

Suppose every `0.x` beta `WelcomeMessageSent` folds up to `1.0.0`, but the `0.9.0` beta needs its own mapping:

[source,java]
----
.register(WelcomeMessageBetaCleanup.build())   // <1>
.register(WelcomeMessage090ToV1.build())       // <2>
----
<1> A broad predicate matching every `0.x` version (`0.x` -> `1.0.0`).
<2> A specific transformer for `0.9.0`, registered _after_ it (`0.9.0` -> `1.0.0`).

A stored `0.9.0` event matches both.
The chain applies the *last* one — the concrete `0.9.0` transformer — producing `1.0.0`, which no transformer matches further, so the broad predicate never runs for `0.9.0` while still handling every other `0.x` version.
Swap the two registrations and the broad predicate would win for `0.9.0` instead.

[NOTE]
.What the chain validates, and when
====
A transformation that changes an event's qualified name (a rename) is rejected when the chain is built — or, with a predicate `from`, when a matching event is read.
A typed mapper whose output identity differs from its declared `to`, and a cycle that exceeds the safety bound, are likewise reported as a `ChainConfigurationException`, but only when the offending event is read.
Overlapping matches are not an error: they resolve by last-match-wins, as above.
====

== Writing safe mappers

A mapper is invoked many times — once per matching event, every time those events are read.
Keep it a pure function:

* *Deterministic* — the same input always produces the same output. No clocks, randomness, counters, or calls to external services.
* *Side-effect-free and thread-safe* — no mutable shared state; do not publish messages, write to a database, or mutate the input.

These rules keep replays reproducible and let the chain run while events stream concurrently.

== Testing a transformation

Because a transformation is a deterministic function from one payload to another, you can verify it in isolation — no event store and no running application.
Build the transformer, feed it a sample stored payload, and assert on the transformed output.

The xref:message-transformation:demo.adoc[course catalog example] does this with a small `given`/`when`/`then` harness, `TransformationTester`, that builds a one-transformer chain and runs the sample event through it:

[source,java]
----
TransformationTester.forTransformation(CoursePublishedV1ToV2.build())        // <1>
                    .given()
                    .messageType(COURSE_PUBLISHED, "1.0.0")                  // <2>
                    .payloadFromResource("/transformations/coursepublished/v1.json")
                    .when()
                    .then()
                    .success()
                    .outputType(new MessageType(COURSE_PUBLISHED, "2.0.0"))  // <3>
                    .outputPayloadFromResource("/transformations/coursepublished/v2.json");
----
<1> The transformer under test, built from its `from`/`to`/`transform` definition.
<2> The stored event to feed in: qualified name, version, and payload.
<3> Assert on the output — its new type and payload.

`TransformationTester` is a few lines of test code in the example, not a framework dependency; copy it into your own project, or assert on the built transformer however you prefer.

[NOTE]
.Untyped output is not identity-checked
====
When a mapper returns a typed object, Axon Framework resolves its identity and raises a `ChainConfigurationException` if it does not match the declared `to`.
When a mapper returns a structural payload — a `JsonNode`, a `Map`, or raw bytes — that check is skipped and the declared `to` is trusted as-is.
The transformations on these pages all return `JsonNode` or `Map`, so the framework cannot catch a wrong-shaped output for you — cover them with tests like the one above.
====

To verify the handlers and projectors that consume transformed events end to end, see xref:testing:index.adoc[Testing].
