= Configuring Transformations
:navtitle: Configuring transformations

Individual transformations are assembled into an `EventTransformerChain` and registered once with your configuration.
Axon Framework then applies the chain whenever events are read from the store.

== Registering the chain

Build the chain with the transformers in the order they should run, then register it as a component:

[source,java]
----
public static EventTransformerChain chain() {
    return EventTransformerChain.builder()
                                .register(SystemAnnouncementLegacyUplift.build())
                                .register(CoursePublishedV1ToV2.build())
                                .register(CoursePublishedV2ToV3.build())
                                .register(StudentRegisteredV1ToV2.build())
                                .register(WelcomeMessageBetaCleanup.build())
                                .build();
}
----

[tabs]
====
Configuration API::
+
--
Register the chain as a component on your `EventSourcingConfigurer`:

[source,java]
----
configurer.componentRegistry(registry -> registry
        .registerComponent(EventTransformerChain.class,
                           config -> CourseCatalogTransformations.chain()));
----
--
Spring Boot::
+
--
Expose the chain as a bean; Axon's auto-configuration registers it for your event store:

[source,java]
----
@Bean
public EventTransformerChain eventTransformerChain() {
    return CourseCatalogTransformations.chain();
}
----
--
====

The chain is built once at startup and is immutable afterwards.

== Why ordering matters

A stored event flows through the chain, with each matching transformer's output feeding the next, until no further transformer matches.
Register transformers in version order so each hop hands off to the one after it:

[source,java]
----
.register(CoursePublishedV1ToV2.build())   // 1.0.0 -> 2.0.0
.register(CoursePublishedV2ToV3.build())   // 2.0.0 -> 3.0.0
----

A stored v1 `CoursePublished` is lifted to v2 by the first transformer, then that result is lifted to v3 by the second, so your handler always receives the current shape.

[NOTE]
.Safety bound
====
The chain stops re-applying transformers to an event after a fixed number of hops (100 by default) to guard against accidental cycles.
If a single event legitimately needs more hops, raise the bound with `EventTransformerChain.builder().maxIterationsPerEvent(int)`.
====

== Writing safe mappers

A mapper is invoked many times — once per matching event, every time those events are read.
Keep it a pure function:

* *Deterministic* — the same input always produces the same output. No clocks, randomness, counters, or calls to external services.
* *Side-effect-free and thread-safe* — no mutable shared state; do not publish messages, write to a database, or mutate the input.

These rules keep replays reproducible and let the chain run while events stream concurrently.

== Testing a transformation

Because a transformation is a deterministic function from one payload to another, you can verify the mapping in isolation — no event store and no running application.
Keep the mapping in a method you can call directly, feed it a sample input payload, and assert on the output:

[source,java]
----
@Test
void liftsV1PayloadToV2() {
    JsonNode v1 = readJson("/transformations/coursepublished/v1.json");

    JsonNode v2 = CoursePublishedV1ToV2.map(v1, null);

    assertThat(v2.get("minCapacity").asInt()).isEqualTo(50);
    assertThat(v2.get("maxCapacity").asInt()).isEqualTo(50);
}
----

To verify the handlers and projectors that consume transformed events end to end, see xref:testing:index.adoc[Testing].
